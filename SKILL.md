# Checking Token-Per-Second Speed

The goal is to give a defensible tok/s number, not just one number pulled from a UI. The same session usually has two very different speeds:

- **Generation throughput**: tokens generated while the model is actively streaming. This is the number to quote for "how fast was the LLM running".
- **End-to-end throughput**: tokens generated divided by total wall time, including tool execution, approvals, retries, and idle gaps. This is useful for "how long did the turn take", but it is not the model's decode speed.

Report both when possible, and say which one is which.

## Quick start

Run the bundled script with a T3 thread ID (UUID) or an OpenCode session ID (`ses_...`):

```bash
python3 scripts/token_speed.py 56de57b4-276a-4fbf-b31a-6383099883e2
python3 scripts/token_speed.py ses_eb111e836ffe8gKJUhsnq1J0oD
python3 scripts/token_speed.py <thread-or-session> --json
```

The script reads the local databases read-only. It is safe to run while T3 Code and OpenCode are running.

Default data locations:

| Store | Path |
|---|---|
| T3 Code state | `~/.t3/userdata/statev2.sqlite` |
| OpenCode messages | `~/.local/share/opencode/opencode.db` |

Override them with `--state-db` and `--opencode-db` if the user has a different data directory.

If the script cannot be used, follow the manual method below. Prefer the script when it works: it handles run boundaries, shared sessions, and percentile calculations consistently.

## What counts as a generated token

For OpenCode assistant messages, each message has a `tokens` object:

```json
{"input": 17335, "output": 78, "reasoning": 17, "cache": {"read": 0, "write": 0}}
```

Use:

```text
generated = output + reasoning
```

Reasoning tokens are generated by the model and cost the same decode time, so leave them in. Do not include `input` or `cache.read`: those are prompt tokens, not generation.

T3 Code v2 also stores aggregate usage on provider turns. In `turnTokenUsage`, the `outputTokens` field already equals `output + reasoning`; `reasoningTokens` is informational. Do not add them a second time. Prefer the raw OpenCode message fields when calculating per-message rates, because they expose the per-message timing.

## Timing definitions

Each OpenCode assistant message stores millisecond timestamps:

```json
{"created": 1792325590167, "streamed": 1792325591854, "completed": 1792325591962}
```

- `created` – request/message start.
- `streamed` – model finished streaming the response. Use this for generation time.
- `completed` – message processing finished. Use this only when `streamed` is missing.

For one message:

```text
stream_seconds = (streamed - created) / 1000
message_tok_s   = (output + reasoning) / stream_seconds
```

For a turn:

```text
generation_tok_s = sum(output + reasoning) / sum(stream_seconds)
end_to_end_tok_s = sum(output + reasoning) / (turn_end - turn_start)
```

Aggregate with sums, not by averaging per-message rates. A 4,000-token message at 200 tok/s carries more weight than a 50-token message at 30 tok/s, and the sum-based rate reflects actual wall time.

Also compute the median and p90 of per-message rates. The median is useful for "typical response speed"; the aggregate is useful for "actual throughput during the turn". A large gap between them is normal when long responses stream faster than short tool-call messages.

## Resolving a thread to its messages

T3 thread IDs are UUIDs. The OpenCode session that served the thread is not the thread ID, and one OpenCode session can serve multiple T3 runs. Resolve it through `orchestration_v2_projection_run_attempts`:

```sql
SELECT run_id, attempt_id, status, payload_json
FROM orchestration_v2_projection_run_attempts
WHERE thread_id = ?;
```

Inside `payload_json`:

- `nativeThreadId` – the OpenCode `ses_...` ID.
- `startedAt` and `completedAt` – the run window.

Then select only assistant messages whose `created` timestamp falls inside that window. This is essential: summing the whole OpenCode session can mix two T3 turns and produce a plausible but wrong answer.

Example: a thread had two runs sharing one `ses_...` session, with an eight-minute gap. Turn 1 generated 48,015 tokens; later runs added more. Summing the whole session would overstate turn 1 and understate its tok/s.

If the user gives only a `ses_...` ID and no T3 thread, split messages into segments at gaps greater than five minutes. The script does this automatically. Label the segments as approximate because a long pause inside one turn can look like two turns.

## Manual SQL fallback

If the script is unavailable, use read-only connections. For a known OpenCode session:

```sql
SELECT data
FROM session_message
WHERE session_id = 'ses_...'
  AND type = 'assistant'
ORDER BY seq;
```

Then parse each JSON row with Python and compute the metrics above. Filter by `time.created` if you have a T3 run window. Do not use `jq` arithmetic on epoch milliseconds without accounting for the `/1000`.

To cross-check aggregate tokens, query the T3 provider turn:

```sql
SELECT payload_json
FROM orchestration_v2_projection_provider_turns
WHERE thread_id = ?
ORDER BY ordinal;
```

`payload_json` contains `tokenUsage` (last request) and `turnTokenUsage` (whole turn). Use `turnTokenUsage` for a quick total, but use OpenCode message timings for tok/s.

## Reporting

Use a compact table or bullets. Always state the model and the time window, then distinguish generation speed from end-to-end speed. If a thread has multiple runs, show one row per run and label running or incomplete runs as partial; do not blend them into one rate. A good answer looks like:

```text
Thread: 56de57b4-... — "Revamp Homepage Header and Hero"
Model: openrouter/deepseek/deepseek-v4.1-flash-1017 (variant max)
Run 1: 12:13:09 → 12:26:32 UTC (803.4s)

Generated: 48,015 tokens (15,435 output + 32,580 reasoning)
Input:     9,564,243 tokens (9,446,400 cached)

Generation: 113.8 tok/s over 421.9s of streaming
End-to-end:  59.8 tok/s over 803.4s wall time
Text-only:   36.6 tok/s (excludes reasoning)
Per-message: p50 76.6 | p75 105.4 | p90 146.9 | max 226.7 tok/s
```

Add one sentence of interpretation:

> The model decoded at roughly 114 tok/s while generating; the full turn averaged about 60 tok/s because most of the 13 minutes was tool execution and other non-generation work.

If the user asks "was it slow", compare against a relevant baseline only when one exists. Otherwise describe the distribution and note that provider load, reasoning effort, output length, and tool calls all affect the number. Do not invent a "normal" target.

## Pitfalls

- **Do not divide by total turn time and call it model speed.** Tool calls, shell commands, approvals, and retries usually dominate wall time. The result will look like a slow model when the model was fast.
- **Include reasoning tokens.** Excluding them makes reasoning-heavy models look slower than they are.
- **Do not count input or cached input as generated tokens.** They are prompt processing, not decode.
- **Respect run boundaries.** A shared OpenCode session can contain several T3 runs. Always filter by the run window or split on large gaps.
- **Check units.** OpenCode timestamps are milliseconds. T3 timestamps are ISO-8601 strings. Convert both to a common unit before subtracting.
- **Skip zero-duration messages.** If a message has no positive `streamed - created` interval, it cannot contribute a meaningful rate. Note the count rather than dividing by zero or silently inflating throughput.
- **Do not average per-message tok/s.** Use total tokens over total streaming seconds for the headline rate.
- **Treat streaming time as approximate decode speed.** It includes time to first token and any provider-side pauses. It is the best local proxy, not a controlled benchmark.
- **Do not compare across models without context.** Variants, reasoning effort, prompt length, cache hit rate, and output length all change throughput.

## If the user wants a comparison

Compute one row per turn or session with the same method, then compare generation tok/s, not end-to-end tok/s. Include token counts and wall time so the comparison is auditable. If two turns used different reasoning variants or output lengths, say so before drawing conclusions.
